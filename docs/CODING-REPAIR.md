# 在 Coding 工作空间验证修复

打开服务端项目，在审批策略菜单的「执行方式」选择「检查与修正」，并给出可复现的症状。例如，项目中有以下两个文件。

```python
# labels.py
def label(value):
    return value
```

```python
# test_labels.py
from labels import label

def test_whitespace():
    assert label(" A ") == "A"
```

发送「修复 label 没有同时清除首尾空格的问题。先运行 test_labels.py 复现，再修改实现并重跑同一个文件。」需要在已开启命令工具、通过 Linux bubblewrap 自检的服务端项目中，以有执行权限的账号运行。批准策略仍适用。

`verify_tests` 接受 `node` 或 `pytest` 和一个相对路径的测试文件。对应运行器及仓库依赖必须在隔离环境内可用。每次检查针对一个过滤后的只读工作区快照。文件过大、受限、执行器缺失或运行中断均可能使验证无法完成。本机目录和团队执行暂不提供这个定向测试工具。

在这个例子里，改成 `value.lstrip()` 仍会失败。如果模型在改动后测试失败却准备结束本轮，运行时可以把失败反馈交回模型一次，继续修正并重跑。最终要检查的是 `value.strip()` 或其他候选实现能否通过同一个目标测试。多改一次文件后，新的内容需要重新验证。

回合卡片分别显示目标文件、实际执行的用例数、退出码、快照摘要和已记录的基线失败。零用例、环境受阻、尚未验证和过期均有独立状态。目标测试通过只说明该快照在选定测试上的结果。使用第三方仓库或模型新增的测试时，仍需检查测试是否覆盖原始问题；正式评测应保留独立评分端。

## 重放回归

从 `coding-agent` 目录运行以下测试。测试使用本机回环模型响应和临时仓库。

```sh
node --test test/repair-loop-integration.test.mjs
```

前两项覆盖无执行权限和固定反馈的继续修正。第三、四项通过服务端 JSONL 入口，在实际 Linux 沙箱中分别检验修复全过程和缺失依赖。后者应产生 `BLOCKED` 事件，界面显示“验证受阻”。普通跨平台测试允许缺少沙箱时跳过；设置 `REPAIR_REQUIRE_SANDBOX=1` 可强制两项实跑。`REPAIR_EVIDENCE_DIR` 可指定新目录，保存验证事件和回环请求数。

Python 评测会在同一个会话的首轮交付和最终交付处分别保存候选文件，然后在求解工作区之外运行隐藏验收。镜像构建、离线验证、留出题和逐题结果字段见[配对评测说明](../evaluation/repair-pairs/README.md)。
