# M041：文件工具崩溃恢复与重试隔离

日期：2026-10-31。基于 M040 `b3f59ec18ee92a0811fd62809b80883b10428b63`，分支 `m041/file-recovery`。用户随后明确授权推送与上线：产品提交 `4722b997` 已推送到 main，并部署为 `m041-20261031-2a74683a75ba`。后续 CI 修复仅改测试与工作流，不改变线上产品逻辑；M040 的独立模型评测基线保持不变。

## 问题与保证范围

`edit → 文件落盘 → 成功结果尚未返回 Java → Node 崩溃` 是结果未知窗口。通信失败不能证明文件未修改；请求去重也不等于文件操作去重。

本轮为服务端单智能体受控 `write/edit` 增加持久化意图、原子替换、结果记录与 Java 独立核对。目标是保留已有文件、拒绝盲目重放，并将无法判断的状态显式交给用户检查。**不承诺所有工具及整个任务严格恰好一次，不自动回滚，也不自动重跑失败任务。**

## 写入协议

1. Java 先保存新任务状态，再消耗旧恢复确认；在启动 Node 执行前保存进程 PID。Java 重启将遗留活动任务标记为中断，不将活着的孤儿进程当成已退出。
2. 每轮拥有独立、位于模型工作区外的操作目录。操作键为该轮的工具调用 ID 的 SHA-256；记录账户、项目、会话、任务、智能体身份以及规范化路径、参数哈希、修改前后内容哈希。
3. Node 用独占锁限制该轮写入；先持久化并同步 `PREPARED` 记录，再写同目录临时文件并同步。目标文件替换前再次核对内容及路径；发现外部修改就中止。
4. 通过同目录 rename 替换目标，保留既有文件的模式位；Linux 同步目录，然后持久化 `APPLIED`，最后才返回工具成功。临时文件受保护，不出现在普通项目文件列表中。
5. 已记录完成的同操作 ID、同参数，且文件仍与预期结果一致时，返回原回执，不再次修改。参数不同、已有不确定操作或内容改变时拒绝重放。
6. 意外退出保留日志及锁；Java 只读核对实际文件，不根据 stdout 缺失推断“未执行”。锁不被静默抢占。新一轮使用新日志目录。

Windows 不支持此处使用的目录 fsync。验证针对进程崩溃，不能推广为任意断电、磁盘损坏或所有文件系统的持久性保证。Java 会话文件采用已有临时文件替换机制，同样不宣称跨文件事务或断电事务。

## 如何解释核对结果

| 当前文件与记录 | 页面含义 | 恢复行为 |
| --- | --- | --- |
| 与 afterHash 相同 | 当前内容与预期修改一致 | 保留内容；PREPARED 仍不能伪装成收到成功回执 |
| 与 beforeHash 相同 | 当前内容与修改前一致 | 不证明历史上从未写过：可能被改回，不能自动重放 |
| 前后哈希相同 | 无法区分是否执行了无变化写入 | 展示歧义，不能证明执行历史 |
| 与两者均不同 | 内容已分歧 | 不覆盖，用户核对并接受当前文件后才允许新任务 |
| 记录损坏、路径不安全、文件超限或无法读取 | 无法验证 | 拒绝解除恢复保护，保留现场供人工处理 |
| Node PID 仍存活或锁不可验证 | 旧执行尚未排除 | 拒绝继续，不擅自终止未知进程 |

`APPLIED` 是执行器持久化的完成记录；哈希是恢复时读取的现状证据，两者在页面上分别展示。后续正常修改也可能使早先操作显示分歧，不应把它解释为写入一定失败。

## 用户重试与确认

- 相同请求 ID、相同提交内容返回已有任务，不启动第二次执行；同 ID 不同内容被拒绝。
- 新请求 ID 或另建会话不能绕过同项目的中断检查。
- 页面通过 `GET /projects/{id}/recovery` 展示报告，明确点击“我已检查文件，接受当前状态”才调用接受接口。这是接受当前文件，不是把旧任务标记成功。
- 服务端确认凭据绑定待恢复轮次、操作记录和当前受支持项目文件内容。检查后文件又改变，接受和下一次提交都会重新核对并拒绝旧凭据。
- 下一轮从新 SDK 会话开始，提示先读取当前文件，不续跑残留工具调用。它仍是模型驱动的新任务，不能数学保证模型不会提出语义上重复的改动。
- 新任务状态先持久化，再清除旧恢复标记。两个步骤之间或清除后、启动前崩溃，重启仍有活动任务可转为中断，恢复检查不会被凭空消耗。

## 明确未解决的边界

- 本机浏览器/桌面目录仍返回 `LOCAL_UNVERIFIED`，Java 不能读取用户电脑文件；本轮只有人工核对门禁，没有新增原生本机持久化操作日志或对本机命令的自动核验。桌面打包清单已包含新模块，不代表发布了新客户端。
- 团队产物发布、shell 命令、MCP/A2A 和外部系统副作用没有因此获得恰好一次语义。它们需要各自的幂等协议、回执与补偿设计。
- 现有单 Java 实例调度不等于多实例分布式锁；独立外部程序在最后哈希检查与 rename 之间竞争仍有窗口。本轮未实现通用文件系统 CAS。
- PID 重用可能保守阻止恢复；损坏日志、超过有界核对额度的工作区需要人工排查。没有自动篡改日志、清锁或删除现场的快捷入口。
- 多文件修改没有整体事务；某些文件完成、另一些未执行是正常可见状态。旧版已经终态、且没有恢复标记的历史任务没有批量迁移；新版本执行及启动时发现的遗留活动任务适用新门禁。
- 哈希匹配仅证明当前字节，不证明唯一执行历史；人工确认后的新模型轮次仍可能选择重复或覆盖操作。系统阻断的是无检查的旧任务/工具重放，而不是所有业务语义重复。

## 面试口述

“Java 不能单凭 Node 崩溃判断修改失败，所以我没有把失败重试做成重新跑整个任务。现在服务端 write/edit 会先保存操作 ID、目标路径和前后哈希，再用临时文件原子替换，最后保存完成记录。Node 在文件写完但回执没送回时退出，Java 可以独立读取日志和实际文件，区分当前内容与修改前一致、与预期结果一致、已经分歧或无法核验；这些描述的是现状，我不会把哈希匹配说成严格的执行历史证明。

同请求 ID 返回原任务；新请求 ID、新会话也绕不过项目恢复检查。用户核对并接受当前文件后才允许新一轮，确认后文件又变了就拒绝旧确认，新轮从干净的工具会话先检查文件。已完成的同操作 ID 能复用回执，不确定的操作不会盲目重放。我用真实杀 Node 的四个故障点，在 Windows、Linux 以及 Java 集成层验证了这一点。

这个保证目前针对服务端受控文件工具和单实例调度，不覆盖本机原生执行、任意外部命令和分布式副作用，也不是整个任务严格恰好一次。这层保护已随 M041 部署，真实杀进程验证在隔离测试环境执行，未在用户生产任务上注入崩溃。”
