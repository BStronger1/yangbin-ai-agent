## 实际能力

18个技能入口 = 16个文本技能 + 原有2个出行技能，覆盖9个领域：

| 领域 | 技能 |
| --- | --- |
| 办公提效 | 会议纪要、周报与复盘、演示故事线 |
| 内容创作 | 长文创作、短视频脚本 |
| 营销销售 | 营销活动策划、广告文案变体 |
| 电商运营 | 商品详情文案、电商内容排期 |
| 产品研发 | 产品需求梳理、交互方案评审 |
| 数据分析 | 业务数据解读 |
| 学习教育 | 学习计划、概念讲解 |
| 求职成长 | 简历表达优化、面试准备 |
| 生活出行 | 城市出行规划、雨天室内安排 |

8位伙伴为演示策划、营销策划、内容创作、短视频编剧、产品经理搭档、数据解读、办公整理和面试准备。每位伙伴绑定一项文本技能，是角色/工作方法入口，不是8个自主协作Agent。16技能共享文本执行器，但具有各自指引与输出契约；不是16套工具链。

文本任务真实接入现有appChatModel的ChatClient.call，系统指引+技能名称/指引+用户材料构成一次逻辑生成。当前只处理用户粘贴文本，不自动检索网页/个人知识库、不执行代码、不生成PPTX/图像/视频。演示技能输出逐页大纲和讲稿，数据技能仅做文本解读，计算/统计需要复核；营销方案不宣称已产生转化收益。上述边界在卡片详情/工作页中可见。

插件能力仍在原入口独立使用，不自动加入文本任务。出行技能跳转原工作流，没有向通用文本执行器提交。现有技能编辑器只编辑出行技能；文本技能/伙伴暂由服务端目录维护，不支持用户自定义角色或导入任意技能包。

## 后端与数据契约

- WorkCatalog读取src/main/resources/work/catalog.json，校验目录ID/版本/类型及伙伴到技能的绑定。
- WorkService使用app.work.dir，默认tmp/work/{owner}/；library.json保存技能/伙伴选择，UUID.json保存文本任务。不能跨账号列出或读取任务；标题列表不包含原始材料/全文结果。
- GET /api/ai/work/catalog、GET /library、PUT /library/{skill|partner}/{id}（selected布尔值）。
- GET /runs、GET /runs/{id}、POST /runs（requestId UUID、skillId、可空partnerId、prompt）。
- 输入1–12000字符，输出非空且最多40000字符；每账号最多100条记录、最多1个RUNNING文本任务。当前未提供记录删除/归档接口，达到上限会明确拒绝。
- 模型调用前原子保存RUNNING、技能/伙伴快照、原始输入及ExecutionProvenance（代码/配置模型/输入hash）。相同requestId与内容重放返回已有状态；同ID异内容409，不重复发起逻辑调用。
- 正常结果SUCCEEDED；模型异常FAILED并仅保留通用错误，原始上游异常不返回。服务重建将遗留RUNNING标为INTERRUPTED，不自动再调用。
- 同步POST执行模型；浏览器可轮询已保存的任务。网络不确定时保留未知状态，提示刷新确认，不能当失败自动重试。当前没有服务端取消、队列调度或独立任务级硬超时。
- 这些保障只限定本执行器的一次逻辑调用，不保证SDK/供应商精确一次计费。单实例JSON存储，不支持多实例并发共享目录。
- 修改/移除收藏不改变既有任务快照。用户材料与结果是账号私有数据，不应进入公共日志/交接；此轮证据均为合成材料。
- 前端身份/路由切换取消读取并忽略迟到响应；同页面后续提交用独立提交序号隔离迟到返回。输出按转义文本呈现，不渲染任意HTML；下载仅为本地Markdown Blob。
