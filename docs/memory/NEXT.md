## 推荐下一轮：独立评测第一版（未开始）

目的：用可复现证据解释Agent完成了什么、纠错是否有效、成本与时延是多少。

1. 先检查现有Task事件/指标、PlanQuality与PlanRepair数据结构，确认能直接读取的字段；避免为看板再次调用模型。
2. 设计独立于现有26例规则开发集的小型任务集：正常、无天气、缺少地点、无依据断言、版本冲突、修订无改善等。明确哪些为模拟/规则回放，哪些需要新模型任务；固定输入、规则版本和预期，保留独立评审标签。
3. 做可重复运行的离线评测入口，产出逐例JSON/CSV：任务完成、结构约束、来源对应、规则告警、修订准入、失败原因。真实语义正确性需人工标签，不能用零告警替代。
4. 持久化评测runId、时间、代码/模型/规则/数据集版本与输入hash，保留原始失败和前后产物；开发集与独立集分别展示。
5. 再做只读评测看板：清晰显示分母、时间范围、样本来源、有效耗时与缺失值。逻辑调用次数与上游请求区别；缺失Token或价格不能伪造费用。

验收：固定输入可复现；历史任务/repair ledger不改写；含失败案例；owner隔离；页面数字可追溯到逐例记录；明确“未测/不可用”。真实模型评测按当前用户授权范围执行，绝不重置既有方案的一次纠错次数。

建议工作顺序：数据契约与离线报告 → 少量案例核验 → 只读看板 → 真实新任务抽样 → 决定下一项优化。
